# Выбор и настройка мониторинга в системе

## 1. Мотивация

Сейчас к сайту подключена Яндекс Метрика, но она видит только онлайн-магазин. После открытия API заказы приходят от партнеров, а сам заказ проходит через магазин, MES, CRM и RabbitMQ. Эти участки Метрика не показывает, поэтому полной картины по заказам нет.

Проблемы обнаруживаются по жалобам, а не по системе. Клиенты и партнеры ежедневно сообщают, что заказ не получен; операторы жалуются на медленный дашборд MES. К моменту жалобы заказ уже просрочен, а компания уже потеряла несколько крупных контрактов.

Мониторинг даст компании:

- раннее обнаружение проблемы — до жалобы клиента или партнера;
- понимание, на каком участке встал конкретный заказ;
- данные для решений о масштабировании частей системы;
- измеримый уровень/сроки обслуживания для партнеров и аргумент в переговорах;
- меньше ручного разбора инцидентов силами поддержки и команды.

Для бизнеса это дешевле, чем потеря контрактов и ручной поиск заказов. Без метрик невозможно доказать эффект и остальных улучшений: непонятно, стало ли лучше и где именно.

Важно: мониторинг не чинит проблемы. Он делает их видимыми и измеримыми, чтобы решения принимались по данным, а не по жалобам.


## 2. Выбор подхода к мониторингу

| Часть системы | Подход |
|---|---|
| Shop API, CRM API, MES API, партнерский API | RED |
| Интеграция MES ↔ CRM: поток сообщений | RED (адаптированный) |
| EC2, Managed БД, брокер RabbitMQ | USE |
| Бизнес-поток заказа | Бизнес-метрики (вне подходов) |

**RED (Rate, Errors, Duration)** — для API и потока сообщений:

- Для API:
  - Rate — сколько запросов или сообщений приходит; 
  - Errors — сколько завершилось ошибкой; 
  - Duration — сколько длится обработка. Это ровно те вопросы, которые важны бизнесу: заказ принят, не потерян, обработан вовремя;
    - для API Duration считаем отдельно по успешным и ошибочным ответам: иначе быстрый HTTP 500 маскирует проблему;
- для очереди RED адаптируем: 
  - Rate — сообщения в секунду на входе и на обработке; 
  - Errors — используем Dead Letter Queue (DLQ); 
  - Duration — время от публикации до обработки. 

**USE (Utilization, Saturation, Errors)** 
— для инфраструктуры: EC2, Managed БД, брокер RabbitMQ. Отвечает на вопрос — хватает ли ресурсов.


## 3. Метрики

### 3.1. Duration — время ответа

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| Response time (p50/p95/p99), отдельно успешные и ошибочные | Shop API, CRM API, MES API | Показывает, где ждет пользователь; база для SLA и дашбордов | `service`, `environment`, `route`, `method`, `status_class` |
| Время загрузки первой страницы MES (p95) | MES, дашборд | Операторы жалуются на долгую загрузку; фильтр и пагинация не помогли — нужен измеримый показатель | `service`, `environment`, `page` |
| Время расчета 3D (p50/p95), отдельно успешные и ошибочные, B2C и B2B | MES, расчет стоимости | Расчет 2–30 минут — главный ограничитель роста; нужно видеть деградацию и разницу между B2C и B2B | `sales_channel` (b2c/b2b), `result` (success/error), `complexity_bucket` |
| Время доставки сообщения: от публикации до обработки (p95) | RabbitMQ, MES ↔ CRM | Показывает, не застревают ли заказы в очереди | `queue`, `producer`, `consumer`, `environment` |

### 3.2. Rate — нагрузка

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| RPS | Shop API, CRM API, MES API | Нагрузка растет примерно на 100 заказов в месяц; нужен тренд и база для остальных метрик | `service`, `environment`, `route`, `method` |
| RPS per user | Shop API, CRM API, MES API | После открытия API один партнер может перегрузить систему; видно источник нагрузки | `service`, `environment`, `client_id`; для `user_id` — ограниченное хранение |
| Simultaneous sessions | Shop API, CRM API, MES API | Сколько пользователей и операторов работает одновременно; помогает отличить рост нагрузки от деградации | `service`, `environment` |
| KB received / sent | Shop API, CRM API, MES API | Объем трафика, в том числе загрузка 3D-файлов; влияет на скорость и стоимость | `service`, `environment`, `direction` |

### 3.3. Errors — ошибки

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| Number of HTTP 500 | Shop API, CRM API, MES API | Прямые ошибки сервиса; всплеск означает инцидент | `service`, `environment`, `route`, `status_code`, `error_type` |
| Number of HTTP 200 | Shop API, CRM API, MES API | Знаменатель для доли ошибок; без него 500 не интерпретировать | `service`, `environment`, `route`, `status_code` |
| Number of DLQ letters | RabbitMQ | Сообщение не обработалось и ушло в DLQ — потенциально потерянный заказ | `queue`, `vhost`, `environment`, `reason` |
| Дубли и потери сообщений | MES ↔ CRM | Интеграцию писала команда; дубли и потери напрямую бьют по заказам | `queue`, `event_type`, `environment` |

### 3.4. Saturation — насыщенность (USE)

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| CPU % | Shop API, CRM API, MES API (EC2) | Один инстанс на приложение: упор в CPU сразу ведет к деградации | `service`, `instance`, `environment` |
| Memory Utilisation | Shop API, CRM API, MES API | Утечки и нехватка памяти при одном инстансе | `service`, `instance`, `environment` |
| Memory Utilisation | Shop DB, MES DB | Managed БД с одним инстансом; нехватка памяти деградирует запросы | `db_instance`, `environment` |
| Number of connections | Shop DB, MES DB | Исчерпание соединений — типичная причина отказов под нагрузкой | `db_instance`, `database`, `environment` |
| Size of DB instance | Shop DB, MES DB | Рост данных и риск упереться в лимит или диск | `db_instance`, `environment` |
| Size of S3 storage | 3D Files Storage | 3D-файлы растут вместе с числом заказов; влияет на лимиты и стоимость | `bucket`, `environment` |
| Consumer lag / queue depth | RabbitMQ | Очередь наполняется быстрее, чем разбирается — saturation интеграции | `queue`, `consumer_group`, `environment` |
| Number of messages in flight | RabbitMQ | Сообщения взяты в работу, но еще не подтверждены — признак затора у консьюмеров | `queue`, `vhost`, `environment` |

### 3.5. Бизнес-метрики

| Метрика | Где | Зачем | Ярлыки |
|---|---|---|---|
| Число заказов по статусам (воронка) | Shop, CRM, MES | Видно, сколько заказов дошло до производства и где теряются | `status`, `source_system`, `environment` |
| Общее время выполнения заказа (p50/p95) | Shop, CRM, MES | Главная бизнес-цель — три недели; показывает, укладывается ли заказ в срок целиком. p50 — типичный заказ, p95 — хвост с просрочками | `sales_channel` (b2c/b2b), `environment` |
| Время в статусе (p95) | Shop, CRM, MES | Видно, какой статус съедает срок | `status`, `source_system`, `environment` |
| Число заказов с превышением нормы времени в статусе | Shop, CRM, MES | Явный список нарушений: сколько заказов уже вышло за срок и в каком месте. Долю считаем от всех заказов в статусе | `status`, `source_system`, `sales_channel`, `environment` |
| Заказы под риском просрочки (прогноз) | Shop, CRM, MES | Прогноз по каждому заказу: `deadline` и `ETA`. Позволяет вмешаться до нарушения срока, а не после жалобы | `risk_level` (red/yellow), `status`, `sales_channel`, `environment` |
| Число заказов от партнеров через API | Партнерский API | B2C и B2B раздельно: жалобы партнеров идут по своему каналу | `client_id`, `environment` |
| Доля успешных расчетов 3D | MES | Если расчет падает, заказ не получает цену и не идет дальше | `sales_channel`, `result`, `environment` |

`sales_channel` — канал продажи: `b2c` (онлайн-магазин) или `b2b` (партнеры через API). `source_system` — система, в которой произошло изменение статуса (`shop`, `crm`, `mes`).

Прогноз просрочки считаем по каждому заказу: `deadline` = время `SUBMITTED` + 21 день, `ETA` = текущее время + медианная длительность оставшихся статусов по истории (отдельно B2C и B2B), `slack` = `deadline` − `ETA`. Red — `slack` меньше нуля, yellow — меньше 3 дней. В метрики отдаем только счетчики по `risk_level`, список заказов — из timeline.

Общее время считаем по каждому заказу отдельно: перцентили по статусам нельзя складывать. Заказы в работе не входят в выборку завершенных, поэтому рядом смотрим число незавершенных, чтобы метрика не занижалась.

Нормы по статусам согласуются с продактом. Стартовые значения: `PRICE_CALCULATED` — до 30 минут (верхняя граница расчета 3D из описания), `MANUFACTURING_APPROVED` и `MANUFACTURING_STARTED` — до 1 рабочего дня, остальные — по договоренности с производством.


## 4. План действий

Высокоуровневый драфт технического задания:

1. Развернуть Prometheus (self-hosted или Managed Prometheus в Yandex Cloud) и Grafana в prod и release, dev — по необходимости.
2. Настроить в приложениях сбор метрик API по RED: количество запросов, ошибки и длительность для Shop, CRM, MES и партнерского API. Использовать одинаковые названия метрик и ярлыков во всех сервисах.
3. Настроить метрики очереди: скорость публикации и обработки сообщений, ошибки и DLQ, время от публикации до обработки.
4. Настроить метрики инфраструктуры по USE: загрузка, насыщенность и ошибки для серверов, баз данных, RabbitMQ и хранилища 3D-файлов. Где есть встроенные метрики облака — использовать их.
5. Собрать логи всех приложений в одно хранилище на базе ELK: писать их в структурированном виде и со сквозным идентификатором запроса, чтобы связать записи между сервисами. Настроить сроки хранения.
6. Включить трейсинг: передавать сквозной идентификатор запроса между приложениями и очередью, чтобы собрать путь заказа через все системы и видеть, где он тормозит. Трейсы смотреть в Jaeger.
7. Настроить бизнес-метрики: считать из единого timeline заказов число заказов по статусам, время в статусе, общее время выполнения (p50/p95), превышения нормы и прогноз просрочки (`deadline`, `ETA`, `slack`); сверять данные Shop, CRM и MES. Для превышений и риска — выгрузка списка заказов для поддержки: метрики дают счетчики, список берем из timeline.
8. Собрать дашборды в Grafana: по API — RED, по очереди — поток сообщений, по инфраструктуре — USE. Настроить пороги и красную подсветку панелей при их превышении. Настроить общий дашборд на всю систему с "проваливанием" в детальные дашборды.
9. Определение и настройка критичных алертов: выбрать показатели, при которых нужен немедленный сигнал дежурному, и настроить доставку. Остальные пороги остаются красной подсветкой в Grafana.


## 5. Показатели насыщенности

При превышении порога панель желтеет, при критичном — краснеет.

| Показатель | Порог | Почему | Что делаем |
|---|---|---|---|
| CPU и Memory API | 70% и 80% — предупреждение; 85% и 90% — критично | Запас до лимита, инстанс один | Добавить ресурсы, заявка в техподдержку|
| Connections БД | 80% лимита; 90% — критично | Исчерпание — отказ запросов | Поднять лимит и пул, заявка в техподдержку |
| DLQ | больше 0 | Сообщение в DLQ — потеря заказа | Разобрать и отправить повторно |
| Consumer lag | больше 5 минут или рост очереди 15 минут | Очередь разбирается медленнее | Добавить консьюмеров, проверить MES и CRM |
| p95 latency API | больше 1 секунды 5 минут | Пользователь замечает задержку | Разбор по трейсам, заявка в техподдержку |
| Доля 5xx | больше 1%; больше 5% — критично | 1% заметно, 5% — инцидент | Откат или срочный фикс |
| Общее время заказа (p95) | больше 21 дня | Обещали три недели | Заявка в техподдержку и продакту, разбор по статусам |
| Превышение нормы в статусе | больше 0 для `PRICE_CALCULATED` и `MANUFACTURING_APPROVED`; рост по остальным | Заказ уже нарушил срок | Заявка в техподдержку, список заказов на разбор |
| Заказы под риском просрочки | есть red или рост yellow за час | Прогноз уже показывает нарушение | Заявка в техподдержку со списком заказов |
| Размер БД и S3 | больше 80% лимита | Запас на рост и очистку | Заявка в техподдержку на расширение или очистку |
| Время расчета 3D (p95) | больше 30 минут | Верхняя граница по описанию | Разбор нагрузки на MES |
