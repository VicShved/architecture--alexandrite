# Архитектурное решение по кешированию

## 1. Мотивация

Первая страница MES — дашборд со списком заказов в работе по статусам — открывается долго. Фильтр по статусам и пагинация не решили проблему: при каждом открытии MES API снова обращается к MES DB. Операторам нужны самые новые заказы, а после открытия API число заказов и нагрузка на чтение растут.

Кеширование предлагаю внедрить, чтобы решить две проблемы:

- сократить время открытия первой страницы MES;
- убрать повторные одинаковые чтения и снизить нагрузку на MES DB.

В кеширование включаю путь чтения MES API для дашборда: первую страницу списка заказов по статусу, счётчики по статусам и карточку заказа. Источником истины остаётся MES DB.

## 2. Предлагаемое решение

### 2.1. Что кешируем и где

Кешируем первую страницу списка заказов по статусу, счётчики по статусам и карточку заказа. Используем **серверный Redis**: он общий для всех операторов, снижает нагрузку на MES DB и позволяет централизованно удалять устаревшие данные.

Клиентский кеш не подходит: он у каждого оператора свой, его нельзя централизованно инвалидировать, и он не снижает нагрузку на MES DB.

### 2.2. Паттерн кеширования

Используем **Cache-Aside**: MES API читает Redis, при промахе — MES DB, затем кладёт результат в Redis. После изменения статуса API удаляет затронутые ключи.

| Паттерн | Почему |
|---|---|
| **Cache-Aside** | **Выбран:** подходит для чтения, простой контроль инвалидации, при отказе Redis можно читать БД |
| Write-Through | Не подходит: в кеше списки и счётчики, а не одна запись; при смене статуса пришлось бы обновлять много ключей |
| Refresh-Ahead | Не подходит: не отменяет инвалидацию и может отдавать старый список |

### 2.3. Диаграмма последовательности

Диаграмма: [caching_sequence.drawio](caching_sequence.drawio).

**Чтение:** оператор открывает страницу → MES SPA → MES API → Redis. При попадании список возвращается из кеша, при промахе API читает MES DB и заполняет кеш.

**Изменение статуса:** оператор меняет статус → MES API обновляет MES DB → после успешного коммита, до ответа `200`, инвалидирует кеш списков прежнего и нового статуса, счётчики и карточку. Заказ должен исчезнуть из старого списка и появиться в новом.

### 2.4. Инвалидация кеша

Основная стратегия — **удаление ключей после записи**. После успешного коммита MES API удаляет ключи списков прежнего и нового статуса, счётчики и карточку. Фильтр у всех операторов одинаковый, поэтому ключи фиксированные и удалять их просто. TTL 30–60 секунд остаётся только страховкой.

| Стратегия | Почему |
|---|---|
| **Удаление ключей (DEL)** | **Выбрана:** удаление точное, следующий запрос читает свежие данные из MES DB |
| Временная (TTL) | Не подходит как основная: старый статус может отображаться до истечения TTL |
| Полный сброс | Не подходит: создаёт лишнюю нагрузку на MES DB |
